# Week 2 Reflection

Weak passwords and unnecessary open network ports represent two different but related security risks.

A weak password can make an account easier to compromise through guessing, password spraying, credential stuffing, or other attacks. Common passwords are particularly risky because attackers can try known lists of frequently used credentials, and even passwords that mix uppercase, lowercase, numbers, and symbols can still be weak in practice if they're just a dictionary word or keyboard pattern with a suffix - "Password1!" technically satisfies every character-type rule, but it's still one of the first things an attacker's wordlist will try. Building a checker that catches this taught me that character-variety rules and true unpredictability aren't the same thing. Real-world password security should also consider unique passwords per account, password managers, and multi-factor authentication.

Open ports expose network services that may accept connections. An open port is not automatically a security flaw, because many legitimate applications need network access. However, every unnecessary or poorly configured service increases the system's attack surface. An outdated service, weak authentication, or insecure configuration can create opportunities for unauthorized access.

While working on the Nmap portion, I ran into a practical question that turned out to be its own useful lesson: what's actually safe to publish about your own systems in a public GitHub repository? Scanning my own machine and posting the raw output - including my hostname or IP address - would expose more about my personal setup than the assignment needs to make its point. To manage that, I practiced the scanning workflow against `scanme.nmap.org`, a server Nmap's own team maintains specifically so people can test scanning tools legally without touching a real target, and I scanned my own machine separately, reporting the open ports and services without including identifying details like the hostname or IP. This is a small-scale version of a real principle in security work: documentation and disclosure should share what's useful for understanding a risk without unnecessarily broadcasting exploitable specifics about a live system.

The exercise as a whole demonstrates why asset and service visibility matters. By scanning a system, I can identify which services are reachable and decide whether each one is expected and necessary. In real environments, security teams reduce risk by disabling unnecessary services, keeping required services patched, restricting network access, monitoring exposed services, and being deliberate about what operational details get shared publicly versus kept internal.

Overall, secure systems require strong authentication, careful control of network exposure, and judgment about what to disclose and where. A strong password does not compensate for an unnecessarily exposed vulnerable service, a securely configured service does not make a weak account password safe, and neither matters much if operational details are published somewhere an attacker can freely use them.
